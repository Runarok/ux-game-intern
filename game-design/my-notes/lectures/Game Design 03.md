# **1. Core Principle: Planning & Risk Awareness**

* Game development is uncertain → planning reduces failure.
* Every game has **unique risks** (mechanics, visuals, audience fit, etc.).
* You must **identify + communicate risks**, not hide them.
* Investors expect awareness + mitigation strategies, not perfection.

---

# **2. Design Artifacts (Key Documents)**

## **2.1 Concept Pitch (1–3 pages)**

* Purpose: Sell the idea to investors/stakeholders.

* Must include:

  * Genre
  * Target audience
  * Game description
  * Unique/compelling features
  * Market context
  * Estimated cost & timeline

* Focus: **Why this game is worth the risk**

---

## **2.2 Game Design Document (GDD)**

* Length: ~15–50 pages, constantly updated

* Purpose: Align design team, avoid unnecessary changes

* Contains:

  * Core mechanics
  * Features
  * Target audience
  * Game style/vision

* Role: **Non-technical blueprint of the game**

---

## **2.3 Technical Design Document (TDD)**

* Length: 20–1000+ pages

* Purpose: Guide developers in execution

* Contains:

  * Tech stack (engine, APIs, languages)
  * Architecture, pseudocode, assets
  * AI, UI, gameplay systems
  * Risks, deadlines, milestones

* Role: **Technical execution + coordination tool**

---

# **3. Rapid Planning Tools**

## **3.1 Storyboarding**

* Quick, low-cost level/story planning

* Visual sequence of scenes (like a comic strip)

* Includes:

  * Player actions
  * Scene context
  * Sound/music

* Used to test **flow + player interaction early**

---

## **3.2 Mood Boards**

* Visual collage (colors, references, style)
* Helps define **look and emotional tone**
* Iterative → multiple versions required

---

## **3.3 Concept Sketches**

* Early drawings of characters/environments

* Used as references → evolve heavily over time

* Key idea: **Don’t get attached to early designs**

---

# **4. MDA Framework (Core Design Model)**

## **4.1 Mechanics (Rules Layer)**

* Rules, systems, actions, controls
* Example: timers, abilities, constraints

---

## **4.2 Dynamics (System Behavior)**

* Emerges from mechanics interacting

* Examples:

  * Time pressure
  * Teamwork
  * Multiple playstyles
  * Atmosphere

---

## **4.3 Aesthetics (Player Experience)**

* What players feel:

  * Challenge
  * Fantasy
  * Narrative
  * Fellowship
  * Expression
  * Discovery
  * Sensation

---

### **Key Insight**

* Designer flow: **Mechanics → Dynamics → Aesthetics**
* Player perception: **Aesthetics → Dynamics → Mechanics**

---

# **5. Mechanics → Dynamics Examples**

* Countdown timer → Time pressure
* Complementary abilities → Teamwork
* Class/weapon variety → Multiple playstyles
* Lighting + AI + environment → Atmosphere

---

# **6. Dynamics → Aesthetics Mapping**

* Time pressure → Challenge
* Teamwork → Fellowship
* Playstyles → Expression
* Visual/audio design → Sensation

---

# **7. Player-Centric Design**

* Focus: Design with player involvement

* Process:

  1. Identify player needs
  2. Define requirements
  3. Build prototype
  4. Test with users
  5. Refine → repeat

---

### **Important Methods**

* Playtesting (most critical)
* Focus groups
* Paper prototyping
* Ethnographic/cultural checks

---

### **Key Rule**

* Ask **specific questions**, not vague ones

---

# **8. Game Design Stages**

## **8.1 Concept Stage**

* Create idea + pitch document
* Build quick prototypes
* Validate assumptions
* Don’t get attached → ideas may be discarded

---

## **8.2 Elaboration Stage**

* Full development begins
* Iterative cycles (prototype → test → refine)
* Expect problems + surprises
* External testers help reveal blind spots

---

## **8.3 Tuning Stage**

* Final polishing phase
* Remove unnecessary/low-value elements
* Heavy playtesting + bug fixing
* Takes **~30–50% of total development time**

---

# **9. Iteration & Reality of Design**

* Game design is **non-linear and iterative**
* Reuse previous systems where possible
* External feedback is essential (bias exists internally)
* More perspectives → fewer blind spots

---

# **10. Key Takeaways (All Things to Remember)**

* Planning is mandatory; unstructured ideas rarely succeed
* Every decision carries risk → identify and mitigate early
* Separate design (GDD) from implementation (TDD)
* Use quick tools (storyboards, mood boards) before heavy work
* MDA is the backbone: mechanics create experience indirectly
* Player perspective ≠ designer perspective
* Test constantly; assumptions are usually wrong
* Don’t get attached to ideas → iteration will break them
* Most time is spent polishing, not creating
* Involve players and others early → reduces costly mistakes
